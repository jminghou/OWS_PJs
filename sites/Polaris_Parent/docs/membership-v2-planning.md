狀態：核心規劃已獲使用者同意，進入實作設計；除關閉正式環境 mock-payment 入口外，程式及資料庫尚未施工。本文件記錄需求與決策（為什麼、做什麼）；實作方式見 [會員 v2 實作架構](membership-v2-architecture.md)。

## 已確認方向（2026-10-03）

- 舊會員與舊功能未真實營運，現有資料都是測試資料，不構成新版的遷移需求。
- 新會員系統只有一個核心用途：購買本站的客製命理報告。
- 商品有數位版與實體書版。實體書包含數位版，數位版可加購實體書；價格規則尚待決定。
- 參考 Wonderbly 的客製商品導購與購買體驗。
- 官網下單，預定串接綠界科技。使用者計畫先完成購物網站，再申請正式金流；目前付款先做佔位，不實際收款。
- 綠界核准前可開啟「人工收款模式」：會員轉帳，管理者對帳後於後台確認收款。
- 初版綠界只開信用卡，不開 ATM、超商代碼等非即時付款。
- 目前尚無營業登記與統一編號，無法開立統一發票：發票功能先做好結構但以設定關閉，結帳不顯示發票欄位；取得稅籍後再開啟。當月網路銷售額達營業稅起徵點（貨物 8 萬、勞務 4 萬）時須辦理稅籍登記。
- 實體書由合作印刷廠印製並出貨；官網管理者負責交付送印檔、登錄印製與物流單號。
- 會員以 Email＋密碼登入；註冊時以 Email 驗證碼驗證信箱後設定密碼，忘記密碼以 Email 驗證碼重設。
- 價格、加購價、交期與人工收款帳戶之後設定，先作可設定欄位；商品文案與樣本先用占位內容。
- 客製商品不適用七日解除權，付款後不受理取消或退款；重複扣款、未能交付、成品瑕疵等例外依法處理。結帳前須勾選同意。
- 初版不做送禮／轉贈：數位版只交付給購買帳戶。
- 系統依狀態寄送通知信（訂單成立、收款確認、待補資料、報告完成、出貨、逾期取消，以及管理者通知）。
- 填妥名字與生成資料後送出，資料須存入命盤資料庫，由另一套獨立紫微系統接手分析及生產。
- **Email 驗證通過後才保存命盤**：試填資料只留在瀏覽器；驗證登入後，才以會員本人 Email 呼叫紫微 save-and-register。
- 生產時機：先保存資料，付款成功後才開始製作完整報告。未付款的資料不進入完整報告生產流程。
- 官網與紫微系統各自獨立，共享同一個資料庫。官網負責會員資料收集、訂單、付款、發票及後續會員功能；報告分析與生產由紫微系統負責。
- 資料結構：新增 `order_items` 表；付款嘗試獨立成表，對外用嘗試編號，不直接用 `order_no`。通用電商結構放 `packages/commerce`，生產交接、成品權限、出貨放 Polaris 站台。

## 系統分工

| 工作 | 負責系統 |
| --- | --- |
| 會員註冊／登入、聯絡資料 | 官網 |
| 收集、驗證並確認報告主角的姓名及出生資料 | 官網 |
| 建立訂單、付款狀態、電子發票、實體書加購 | 官網 |
| 命盤資料保存 | 紫微系統（官網經 save-and-register 呼叫） |
| 排盤、命盤分析、報告生產 | 獨立紫微系統 |
| 會員查看進度、取用成品、查訂單 | 官網，讀取紫微系統提供的進度與成品資訊 |
| 收件資料與會員查詢出貨 | 官網 |
| 實體書印製與出貨 | 合作印刷廠（系統外）；官網管理者交付送印檔並登錄物流單號 |

### 購買與生產順序

填寫並確認資料 → 註冊（Email 驗證＋設定密碼）或登入 → 保存命盤資料及待付款訂單 → 付款（綠界信用卡或人工收款） → 紫微系統製作完整報告 → 官網提供成品與訂單進度。

### 交接原則

- 付款成功須由後端確認（綠界通知驗證或管理者人工確認收款）；不能僅靠前端返回成功頁或資料已入庫就啟動完整報告生產。
- 每筆製作需求對應會員、訂單項目、命盤資料及其版本；重複送出或通知重送，不重複建單、生產或寄信。
- 付款、製作、出貨、發票各自記錄狀態。付款成功但製作失敗時保留訂單並顯示待處理，由管理者補救。
- 兩套系統依寫入權責矩陣約定各自能寫入的資料及狀態，共用資料庫不代表任意互改資料表。
- 購買者、報告主角、收件人分開保存；一名會員可購買多人的報告，不需替每個主角建立會員帳號。
- 訂單保留送出時確認的出生資料版本；製作開始後的更正透過明確流程處理，不直接改寫已製作的來源資料。
- 加購實體書建立新的加購訂單並關聯原報告版本，避免無意間重新分析。

資料契約、狀態與例外的細節見實作架構 §5–§7。

## 功能方案

### 銷售與購買

商品介紹 → 選數位版／實體書版 → 填寫報告主角資料 → 預覽（內容待定） → 確認資料 → 註冊（Email 驗證＋設定密碼）或登入 → 實體書填寫收件資料（發票功能開啟時另填發票資料） → 勾選交易政策同意 → 保存命盤與待付款訂單 → 付款成功 → 紫微系統製作完整報告 → 官網交付。

資料填寫以製作需求為限，例如姓名或書中稱呼、出生日期、時間、地點，以及排盤引擎必要的欄位。出生時間不確定時應提供說明或協助確認入口，不默填任意時間。付款前集中展示出生資料讓購買者確認。

數位版只索取交付與付款所需資料（發票功能開啟後加上發票資料）；實體書才索取收件人、電話、地址與必要配送資訊。購買者、報告主角和收件人可以是不同的人。

實體書包含數位版，數位購買者日後可加購實體書；價格、抵扣方式與交付時程待確認。購前預覽封面、目錄與部分內容仍是建議，須配合紫微系統的生成能力決定。

### 會員端

- 我的報告：製作進度、已完成 PDF 下載；後續可加購實體書。
- 我的訂單：付款、發票、交付／出貨狀態、物流、訂單客服；人工收款訂單可回填轉帳資訊。
- 帳戶設定：聯絡 Email、登入與必要帳戶管理。

初版採單一會員身分、不分級，以 Email＋密碼登入；註冊時須先以 Email 驗證碼驗證信箱。會員的主要價值是保管購買紀錄及取用報告。購前瀏覽與試填不要求註冊，準備結帳時再註冊或登入，並明確告知會建立購買帳戶。

報告只提供給擁有該筆購買的帳戶。已驗證 Email 才能存取歷史訂單；不可僅因輸入相同 Email 就開放報告。

### 管理端

- 訂單：付款狀態、版本、購買者、報告主角、發票、交付資訊。
- 人工收款：待確認清單、對帳後確認收款（需專屬權限，記錄操作人）。
- 製作追蹤：顯示紫微系統提供的進度、待補資料與失敗原因；重試及更正方式依兩套系統約定。
- 出貨：交付印刷廠送印檔，登錄待送印、印製中、已出貨與物流單號。
- 會員：搜尋 Email，查看對應訂單及報告，處理帳戶問題。
- 商品設定：內容介紹、數位／實體價格、樣本、製作時程與配送設定。

每筆訂單保留付款時確認的出生資料與報告版本。付款後的修改須走更正流程，避免改到已交付報告或已送印的書。關鍵操作保留時間及操作人紀錄。

## 既有資料庫適用性檢查（2026-10-03）

範圍：檢查本機模型、SQL、migration、訂單 API 與統一資料庫架構文件；尚未連線核對實際資料庫，也未檢查獨立紫微系統的最新模型。

結論：沿用同一個資料庫，保留會員與命盤基礎，針對新版購買及交付流程擴充結構。不建議在未補齊資料契約的情況下直接套用舊流程。

- 可沿用：account.app_users、blog.member_profiles、既有命主與命盤資料；shop.products、product_prices、orders 可作為商品及訂單基礎。
- shop.orders 有會員、金額、幣別、付款方式、付款時間及商品 JSONB 快照（`items`，無數量欄位），沒有命盤／報告版本關聯，也沒有生產、交付、配送結構。因此新增 `order_items`。
- 現行 `order_no` 格式為 `ORD-YYYYMMDD-XXXXXXXX`（21 字元、含連字號），不符綠界 `MerchantTradeNo` 規格，所以付款改用獨立的付款嘗試編號。
- shop.payment_methods 是付款方式設定，不是每次交易紀錄；因此新增付款嘗試與通知紀錄表。
- 舊 order_submissions、coupon_configs、reward_grants、saved_articles 屬於舊功能，無需作為新版訂單核心；目前保留封存，不執行刪除。
- 正式金流目前仍是 orders API 內的 TODO；資料表存在不代表付款流程已可營運。
- `POST /webhooks/mock-payment` 原本未驗證身分且不分環境，任何人可將訂單改為已付款；2026-10-03 已改為僅開發模式開放、且只處理待付款訂單。此路由屬 `packages/commerce`，Claire、Happy_Wu 一併受保護。
- 本站保存命盤的現有程式呼叫紫微 save-and-register API，該 API 會同時建立免密碼會員並歸戶；沿用紫微端掌管命盤寫入的方式，但改為 Email 驗證後才呼叫。
- account 與 graph 結構如需變更，由紫微系統管理；官網負責所屬會員擴充及交易表的 migration。避免修改共用套件時改變其他官網行為。
