# 交易資格一致化與製作交付閉環

最新狀態（2026-10-29）：已完成**本機整合環境部署與真實跨系統 API 驗收**，並接續完成通知出站重驗；尚未雲端正式上線。詳細結果與界線見 [本機部署與驗收紀錄](fulfilment-local-acceptance-20261029.md)。以下各批次的「尚未部署」文字保留當時歷史狀態。

## 首批實作：新代客契約與本機履約阻擋

本批擴充既有服務，不新增資料表，不執行正式 migration 或回填。

- 新代客單（含直接接單／零元贈送）即使 foundation 開關關閉也建立契約，再沿用付款確認服務發放資格；不新增官網付款紀錄。部署前必須先確認 0010–0018 所需資料表已備妥。
- 舊外部單即使沒有契約版本也檢查成交證據，不能因 legacy 相容路徑繞過作廢阻擋。
- 排程與人工派工均檢查報告資格；商業阻擋保留原因，不呼叫遠端、不增加網路嘗試次數。
- 打樣上傳、追加修改次數、會員／管理者確認、自動確認使用同一資格檢查。
- 派工及打樣採訂單先於子工作資料的鎖順序。這不等於跨系統競爭問題已解決；本批仍沿用既有派工期間持鎖方式。
- 修正客人檔案隨機密碼偶爾缺少數字而無法建單的問題；保留原有隨機長度，額外保證複雜度規則。

## 第二批：履約暫停／恢復與遠端同步（實作及隔離驗證完成）

- 官網以訂單為範圍，在既有 `Order.attributes.fulfilment_control` 保存 desired、revision、原因、操作人、同步結果與重試時間；每次變更均鎖訂單，並新增稽核事件。不同品項分別暫停尚未開放。
- 暫停立即阻擋本機履約；恢復先重新核對成交證據及所有相關資格，再等待遠端相同版本確認。不能藉恢復操作重新啟用作廢證據或撤銷資格。
- 外部證據作廢同時建立暫停意圖。背景 `fulfilment_controls` 使用既有排程與跨程序鎖，網路同步時不持有訂單鎖；收到回應後再核對版本。
- 失敗採退避重試，第六次起標示需人工處理，仍保留重試；後台可重新排入同步。相同版本的遠端重送不重複記錄，較舊回應不會解除較新暫停。
- 訂單詳情（含無報告工作單的加購）及報告交付頁有控制面板；會員只看到暫停提示，不揭露內部原因。人工派工在手動暫停時回傳 409。
- PolarisUI 新增服務憑證保護的 `POST /public/report-requests/{request_no}/control`；接收版本化暫停／恢復，甚至能先於工作單保存暫停。工作單接單與狀態推進由 SQL 鎖與控制資料共同檢查，後台回傳暫停標示。
- 遠端新增 `account.report_request_controls` 與 `account.report_request_control_events`，migration `0030_fulfilment_controls` 接續 `0029_ziwei_terms`，只新增檔案，尚未套用正式資料庫。

### 本批驗證

中斷前完整回歸：210 passed（7162 warnings）。收尾後重跑受影響範圍：43 passed（1306 warnings）；兩組有重疊，不能相加當作獨立測試數量。前端 TypeScript 無輸出檢查通過，兩個 repo 的 diff whitespace 檢查通過。

`backend/tests/check_fulfilment_remote_postgres.py` 在一次性 PostgreSQL 執行實際 migration 與接收端 SQL，通過先暫停後建單、重複、過期、並行命令、暫停後不可推進、恢復及有紀錄時拒絕回退。這個測試抽取路由函式並替代 HTTP 例外，不載入正式 FastAPI app 或認證；不等於正式跨服務端到端驗收。

### 部署順序及操作

1. 檢查並備份目標資料庫；先在 staging 套用 Polaris 的 0030，再部署接收端。舊工作單會建立 revision 0 的 active 控制列。
2. 部署官網端並確認 `REPORT_JOBS_ENABLED` 或既有排程 CLI 確實運作；兩端服務憑證沿用現有方式，不新增公開權限。
3. 在 staging 以測試訂單驗證「暫停 → 已同步 → 恢復 → 已同步」，並暫時使測試接收端不可用來驗證退避與人工重排。同步未確認前官網維持阻擋。
4. 不可只回退 Polaris 接收端而留下 active 的控制流程；若接收端失去新版支援，官網會維持待同步。已有控制事件時 migration 禁止刪除資料表。

本批未部署、未跑正式 migration、未重新執行瀏覽器操作驗收。暫停只控制工作單及履約入口，不中止已開始的 LLM／排版程序，也不撤回既有下載、送印或出貨；那些情境須人工處理。恢復沿用現有打樣期限，不自動順延。

## 第四批：版本化成品回傳與後台核對交付（2026-10-29）

### 可操作流程

1. 製作端工作單先依既有流程標記完成（外語沿用翻譯審核門檻）。負責人或管理員於完成工作單選擇最終 PDF，登錄成品；上限 100 MB，語系權限仍須符合。
2. 官網後台「報告交付」按「查詢製作端成品」，看到檔名、版本、大小，再按「核對並交付此版本」。不是看到 completed 就自動發布。
3. 官網核對訂單、工作單、會員、命盤、語言、環境與商品，下載後核對大小、SHA-256，再重新讀取成品版本，最後鎖訂單重驗履約資格、暫停與目前交付版本。
4. 成功後沿用私有檔案、會員下載與首次完成通知。重複接收同版本不建立第二份文件或重複通知；更正版須核對目前文件 ID。人工上傳保留，遠端舊版本不能蓋回人工更正。

### 底層與部署

- Polaris 新增 migration `0031_report_artifacts`（接續 0030）：工作單增加 `artifact_revision`，新增不可覆寫的 `account.report_request_artifacts` 版本清單，記錄來源更新時間、歸屬、檔案資訊與登錄人。有成品紀錄時禁止 downgrade 丟棄資料。
- 最終 PDF 存於 `REPORT_ARTIFACT_DIR` 指定的**私有持久磁碟**，以 SHA-256 命名、以 hard link 原子建立；此目錄不得由 Web 伺服器直接公開。需要支援 hard link 的同一磁碟／檔案系統；多副本需共享此持久儲存。未設定時拒絕登錄。備份時需同時保留資料庫和檔案。
- 登錄與版本增加使用同一 SQL 交易，核對預期版本、工作單來源時間、負責人與暫停狀態。並行登錄只有一個能成功。舊成品在工作單重新開啟或更新後無法供官網接收，須重新確認並登錄。
- 服務端成品查詢及取檔沿用 `X-Service-Token`；編輯上傳沿用登入與 `page:editor` 權限。官網新增 `/admin/report-orders/<order_no>/production-artifact` GET／POST，限 `report_orders.fulfill`。
- 官網不新增資料表，使用既有 ReportDocument 與私有儲存，將來源版本記入 `Order.attributes.report_artifact_import` 與上傳稽核。人工上傳和成品接收共用訂單鎖，防止目前文件指標互相覆蓋。
- 部署順序：先在 staging 套用 0031、設定製作端持久私有目錄，再部署製作端 API／UI，最後部署官網。已新增 migration 檔，尚未在正式或既有測試資料庫套用。

### 邊界及驗收

本批接收需要後台明確操作；未新增背景自動交付，也沒有把排版輸出自動選成最終成品。PDF 的內容、語言與排版正確性仍由製作人確認，雜湊只驗證傳輸內容一致。

遠端版本二次確認與官網提交不是分散式交易；不能承諾遠端在最後一次確認之後發生的變更會原子撤回官網已交付檔案。已下載檔案與既有送印不會被回收。成品登錄失敗可能留下未被清單引用的私有檔案，暫不自動清除，以避免誤刪；需後續配置有保留期的清理工作。

隔離測試入口：`backend/tests/test_report_artifacts.py`（官網假傳輸／私有暫存）及 `backend/tests/check_artifacts_remote_postgres.py`（一次性 PostgreSQL、實際 migration／SQL／本機私有檔案）。後者抽取路由函式，不載入正式 FastAPI 或認證中介層，不等同完整 HTTP 驗收。

收尾驗證：官網成品、既有交付、進度、暫停、資格邊界、排程與派工共 **61 passed**（1687 warnings）；製作端一次性 PostgreSQL 測試通過；兩端 TypeScript 及修改格式檢查通過。

staging 操作驗收：完成測試單 → 登錄 PDF → 官網查詢及交付 → 會員下載；再驗證重複操作、更正版、人工更正後舊版拒絕、暫停、重新開啟、錯誤版本與中斷連線。瀏覽器與真實跨服務驗收尚未執行。
