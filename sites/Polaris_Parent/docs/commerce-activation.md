# 階段 0 第二批：帳號綁定啟用碼

實作日期：2026-10-14。未部署、未操作正式資料庫、未發送任何真實啟用碼。

## 行為與邊界

啟用碼領用一份既有資格，不建立付款、不增加製作次數、不轉移訂單或出生資料的歸屬。資格持有人、操作者、訂單購買者必須是同一會員，兌換需要登入且 Email 已驗證。

一般官網訂單不需要啟用碼。管理者對某項已付款、尚未使用且未關聯任務的資格明確發碼後，該資格才須先兌換再使用。畫面會提示此變更。新碼綁定原購買會員，不能任意指定其他收件人。

目前可以對尚未開始的書籍或專人解讀資格發碼。官網數位報告在核款時已建立任務，因此不允許事後改成碼啟用。外部平台訂單尚未匯入；未來須先完成渠道政策設定、付款來源驗證、會員歸屬及報告派工時機設計，才能使用相同核心。不能把本次功能視為 Etsy／Creema／idus 已串接或已允許站外啟用。

## 管理者操作

需要新的 `report_orders.activation` 權限；檢視收款後台另需既有 `report_orders.read` 權限。只有出貨／收款權限的人不會因此得到發碼權限。依既有權限註冊機制同步角色設定。

1. 後台「人工收款」找到已付款訂單，展開「成交明細與製作資格」。
2. 在尚未使用的資格選擇 1–90 天有效期（預設 14 天），確認發放。
3. 明碼只在成功回應及此次畫面顯示一次，關閉後不能查回。系統不寄信、不自行聯絡平台或會員。由管理者依已確認的渠道規則交付指定會員。
4. 若回應遺失或碼遺失，先填原因撤銷，再重新發放；系統拒絕直接重複發放有效碼。
5. 到期可直接補發，舊碼以 `expired_replaced` 原因撤銷。舊碼立即失效。

已兌換的碼不能撤銷或再發。服務要取消時，使用原本書籍／解讀取消及退款流程，會撤銷資格；撤銷未兌換的碼本身不代表退款或取消資格。

## 會員操作

在既有訂單詳情頁可看到需要啟用的服務、到期時間及輸入框。碼僅以 POST body 送出，不放網址。兌換後重新取得同一筆訂單，對應資格可繼續既有設計或安排流程。其他會員即使持有碼也無法兌換，錯誤回應不揭露訂單資料。

| 情況 | 結果 |
| --- | --- |
| 有效碼、指定會員、已驗證 Email | 記錄啟用，原資格解鎖 |
| 同會員再次提交已兌換碼 | 成功回傳原訂單，`redeemed=false`，不新增資格或任務 |
| 其他帳號或碼不屬於畫面上的訂單 | 拒絕兌換 |
| 到期或已撤銷碼 | 拒絕，需補發 |
| 訂單取消或資格撤銷 | 拒絕，不復活權利 |
| 書籍與報告在同一訂單 | 書籍待啟用不妨礙原報告任務 |
| 解讀購買多次，其中一份尚未啟用 | 沿用現行整組預約，整組需等所有相關資格可用才能安排 |

## 資料與併發

新增 `shop.commerce_activations`，migration `0011_commerce_activations` 接續 0010。記錄資格、指定會員、發碼人、SHA-256 雜湊、狀態及時間；不儲存明碼。碼使用密碼學隨機 160-bit 資料並以 Base32 顯示，大小寫、分隔線及空白不影響兌換。

狀態為 `issued / redeemed / revoked`；到期由時間判定，毋須排程才生效。一份資格最多一筆 `issued` 碼，由資料庫部分唯一索引保障。發碼、兌換、撤銷與開始製作都先鎖定同一訂單列；事件紀錄與狀態變動在同一交易提交。

`commerce_events` 記錄發碼、兌換、撤銷的操作人與碼紀錄 ID，沒有明碼。發碼及兌換成功回應使用 `Cache-Control: no-store`；訂單 API 只回啟用狀態，不回明碼或雜湊。API 依既有 limiter 限制發碼每分鐘 10 次、兌換每分鐘 5 次；部署須維持 limiter 啟用及既有儲存設定。

新 API：

- `POST /api/v1/admin/report-entitlements/:id/activation`，body `{ "days": 14 }`
- `POST /api/v1/admin/report-activations/:id/revoke`，body `{ "reason": "遺失補發" }`
- `POST /api/v1/report-activations/redeem`，body `{ "code": "…", "order_no": "…" }`；`order_no` 可省略，訂單頁會提供以防兌換錯筆。

啟用標記寫在發碼訂單的 `attributes.commerce_activation_version=1`。沒有標記的既有訂單不查新表、不增加啟用步驟。讀取成交權限快照與授權操作分開，待啟用時管理者仍能檢視設計資料。

## 部署與回退

1. 在測試環境先執行 migration 至 0011，確認應用程式資料庫角色擁有新表／序列的所需權限。
2. 保持 `COMMERCE_ACTIVATION_ENABLED=false`，驗收舊流程；新建資格仍依 `COMMERCE_FOUNDATION_ENABLED` 控制。
3. 準備測試會員、已核款書籍或解讀資格，再開啟 `COMMERCE_ACTIVATION_ENABLED=true`。
4. 完成發碼、兌換、遺失撤銷補發、取消訂單及權限隔離驗收，再另行安排正式部署。

關閉啟用碼開關會暫停發碼及兌換，但不繞過已存在的啟用限制；管理者仍可撤銷舊碼。故關閉開關不是解除服務等待的方法。需要恢復兌換時重新啟用；需要取消服務時走原取消流程。只要有啟用碼資料，0011 downgrade 就拒絕刪表。回退需保留能辨識啟用標記與檢查資格的程式，不能直接退回不支援啟用碼的版本。
