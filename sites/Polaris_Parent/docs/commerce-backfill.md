# 階段 0 第三批：歷史訂單審查與受控回填

日期：2026-10-14。工具已實作及隔離測試，未盤點或改寫正式訂單。本批沒有新增資料表或 migration，沿用 0010 的成交快照、資格、任務與事件表。

## 可驗收的結果

後台「人工收款」中，具備 `report_orders.backfill` 權限的人可對尚無交易契約的訂單產生預覽，查看：

- 成交金額、成功付款紀錄編號、會員識別。
- 每品項原單價／數量、正規化後的計價單位、印刷份數及計價組成。
- 會建立哪些資格、保留哪個履約狀態、對應哪個既有工作。
- 阻擋轉換的原因，或未付款／已轉換的判定。

人工核對後，須填審查備註並勾選確認，才可逐筆套用。套用不執行核款、不重寄通知、不呼叫外部服務、不更動既有報告／書籍／解讀工作狀態。

新權限與既有收款、出貨權限分開；進入此後台仍需 `report_orders.read`。一般會員無法預覽或套用。依既有權限註冊機制同步角色設定。

## 哪些資料會接受

這一批只處理本站已知商品代碼的台幣人工收款歷史訂單。原會員須存在，訂單與品項總額須一致，且有唯一一筆對得上金額／幣別的 `manual / live / succeeded` 付款，包含核款人及付款時間。沒有成功付款的待付款或未付款取消單只略過，不發權利。

只讀訂單、品項、付款及既有工作上的歷史快照，不查今日商品價格來還原成交條件。原報告／加購／設計的歸屬、實體書的規格／權利／計價組成、物流狀態及取消／退款資料也須一致。缺失或矛盾會阻擋；修復原始證據後重新預覽，不提供略過檢查的強制套用。

各種混合異常可能同時存在，工具先回傳第一個阻擋原因。未實作的商品／幣別／付款模式、未知契約版本、部分已建立的骨架資料均不覆寫。每品項數量超過 1000 也轉人工例外處理。

## 狀態轉換

| 舊紀錄 | 新資格 | 任務 |
| --- | --- | --- |
| 報告已付款，交接 pending／sent／failed，尚無成品 | 使用中 | 關聯原報告工作，started |
| 有唯一有效報告 PDF 且交付時間完整 | 已完成 | 關聯原報告工作，completed |
| 書籍 awaiting_customization | 可使用 | 不建立新製作任務 |
| 書籍打樣中／已確認／印製中／已出貨 | 使用中 | 關聯原書籍工作，started |
| 書籍 delivered | 已完成 | 關聯原書籍工作，completed |
| 書籍 cancelled，取消與退款資料可核對 | 已撤銷 | 關聯原書籍紀錄，cancelled |
| 解讀 to_schedule | 可使用 | 不建立新預約任務 |
| 解讀 scheduled／completed | 使用中／已完成 | 關聯原解讀工作，started／completed |
| 解讀 cancelled，取消與退款資料可核對 | 已撤銷 | 關聯原解讀紀錄，cancelled |

取消紀錄的任務是對既有工作資料的歷史關聯，不表示重新啟動製作。整張已取消但曾收款的加購單，只有所有資格均為撤銷時才可轉換。報告已完成、書籍已取消的混合訂單，兩者各自保留狀態。

報告 `not_ready`／`cancelled` 與成功付款並存、成品與交付時間矛盾、書籍與物流狀態矛盾等情形需要人工釐清，不由工具猜測。解讀仍沿用整組安排／完成，未增加逐次核銷功能。

## 審查與併發保護

預覽會計算來源資料的 SHA-256 指紋，並產生綁定訂單、審查人及轉換規則版本的簽章憑證，有效 30 分鐘。來源資料包含既有設計等紀錄以偵測變更；原始出生、地址、文件路徑等資料不會隨預覽回傳，也不放進憑證。

套用只接受憑證、備註與明確確認；不接受瀏覽器自行提交要發多少權利。伺服器會鎖定訂單，重新產生計畫，核對指紋後才寫入。資料變更、憑證過期、被改寫或換了審查人，都須重新審查。兩人或兩個請求同時套用，只會有一筆轉換事件；同一有效憑證重送回傳 `changed=false`。

舊履約操作也使用相同訂單鎖，並在取得鎖後重新判斷是否已轉換。這避免「請求起初讀到舊版本，等待期間已回填，接著跳過新資格檢查」的競爭情況。

## 實際改寫範圍

- 新增本站來源、成交快照、對應歷史狀態的資格／任務。
- 設定訂單 `commerce_contract_version=1`，其他 attributes 保留。
- 將書籍品項轉為一個計價套組，印刷份數獨立記錄。尤其舊加購的 `unit_price` 原本已是整組金額，不能再乘原 quantity。
- 保留 `orders.items` 原始 JSON 快照、原付款與退款、原履約紀錄。
- `order_backfilled` 事件保存審查人、備註、指紋、規則版本、付款紀錄 ID 與轉換計畫（含原單價／數量）；每份資格另有 `entitlement_imported` 事件。

沒有偽造新的付款成功事件，也不把已完成資格改回可使用。整筆寫入共用同一交易，失敗會全部回滾。成交快照仍以既有資料與人工核對為依據，工具無法自行證明早年的資料從未被人修改。

## 啟用與操作

1. 測試環境先確認既有 migration 至 0011、資料庫角色的表／序列權限，以及穩定且妥善設定的應用 `SECRET_KEY`。
2. `COMMERCE_BACKFILL_ENABLED` 預設 false；關閉時仍可預覽，但不能套用。與新訂單骨架及啟用碼的開關分開。
3. 詳細唯讀盤點可用 `flask --app <site> report_orders commerce-backfill-preview --order-no <編號>`；省略編號會輸出符合既有報告付款模式範圍的訂單。CLI 不給套用憑證、不批次改資料。需使用已核准的環境設定啟動應用；本次沒有執行正式 CLI。
4. 開啟測試環境回填開關，在後台逐筆審查與確認；確認權限、過期／失效憑證、混合完成／取消、重送及原流程相容性。
5. 正式資料另行盤點及核准，先處理例外，再安排逐筆轉換。正式執行前依既有流程備份。

API：`GET /api/v1/admin/report-orders/:order_no/commerce-review` 產生預覽；同一路徑 `POST` 接受 `{ review_token, note, confirmed: true }`。成功回應不快取。備註填對帳依據或處理紀錄編號，避免放入出生資料或完整銀行帳號。

關閉開關只停止新的套用，不撤回已建立資格。既有訂單後續仍走新資格檢查；沒有自動 undo，不能刪除稽核紀錄或退回不認得交易契約的程式。誤轉需另行審查修正，不能用重新回填覆寫。

## 測試與限制

- `test_commerce_backfill.py`：13 項回填專屬案例及 9 項交易骨架相容性案例，涵蓋唯讀、混合終態、多本加購、取消整單、缺少證據、過期或被改寫的憑證、權限／開關、資料變更、今日價格隔離、交易回滾。
- 一次性 PostgreSQL：同時套用只產生一份紀錄；交付請求持有舊 ORM 狀態時，回填後仍能正確完成新資格。
- 前端 TypeScript 檢查與既有流程回歸測試。尚未做瀏覽器視覺驗收，也未證明所有真實舊資料均可轉換。

階段 0 尚待完成渠道政策與外部訂單驗證、派工 outbox／重試、正式金流，以及真實舊資料驗收；本批完成的是受控回填工具。
