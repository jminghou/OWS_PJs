# 親紫之間會員 v2 實作架構

日期：2026-10-03。狀態：實作設計基準，尚未套用資料庫變更或部署。需求與決策紀錄見 [會員 v2 規劃](membership-v2-planning.md)；本文件只寫「怎麼做」。

## 1. 目標與範圍

核心商品為客製命理報告，分數位版與實體書版。實體書包含數位版，已購數位版可加購實體書。官網負責會員、商品、資料收集、訂單、付款、發票與交付入口；獨立紫微系統負責命盤及報告生產，兩者共用資料庫。

已確認流程：填寫並確認資料 → 註冊（Email 驗證＋設定密碼）或登入 → 保存命盤及待付款訂單 → 確認付款成功 → 紫微系統製作完整報告 → 官網供會員取得報告及查詢出貨。

正式金流採綠界科技。現階段完成購物功能與付款佔位，不實際收款；綠界核准前可用人工收款模式小量販售（§3）。正式申請時程不阻擋官網開發。

**初版範圍外**：送禮／轉贈（數位版只交付給購買帳戶）、信用卡以外的付款方式、主動退款流程（僅處理 §10 的例外情形）。其他延後項目見 §13。

## 2. 模組與責任

| 模組 | 責任 |
| --- | --- |
| 商品與版本 | 報告介紹、樣本、數位／實體價格、交付時間 |
| 會員 | Email＋密碼登入、註冊時 Email 驗證、忘記密碼、帳戶資料、本人訂單及成品存取 |
| 客製資料 | 填寫、伺服器驗證、確認頁、保存當次資料版本 |
| 訂單 | 後端計價、訂單項目、版本、命盤關聯、收件資料、加購關聯、交易政策同意紀錄 |
| 付款 | 佔位、人工收款、綠界測試及正式模式；付款嘗試、通知驗證與交易紀錄 |
| 電子發票 | 結帳收集發票選項、付款確認後開立、記錄開立結果（§8） |
| 通知信 | 依狀態轉換寄送會員與管理者通知（§9） |
| 生產交接 | 付款後登記製作需求，接收紫微系統進度與成品識別 |
| 會員交付 | 我的報告、下載授權、我的訂單、實體配送進度 |
| 管理後台 | 會員查詢、訂單查詢、人工收款確認、待補資料、失敗處理、出貨登錄 |

預期初期交易量低，先沿用現有 Next.js、Flask 與 PostgreSQL。以資料庫內持久化的交接紀錄處理兩系統協作；紫微端沒有可用的工作佇列，改由新建的人工工作單承接（見紫微介接契約）。

## 3. 付款模式

後端設定決定目前的付款模式；隱藏或停用前端按鈕不足以保護流程。

| 模式 | 畫面與系統行為 |
| --- | --- |
| 佔位（公開網站初期預設） | 能展示商品、填表、確認並保存待付款訂單；標示「付款功能尚未開放」，不顯示付款成功，不登記完整報告生產 |
| 人工收款（綠界核准前，選用） | 訂單頁顯示匯款帳號、應付金額與期限；會員回填轉帳末五碼及時間；管理者對帳後於後台「確認收款」，之後與正式付款走同一條交接流程 |
| 測試（隔離環境） | 使用綠界測試環境驗證付款跳轉及通知；測試訂單只連到測試生產資料，不得啟動正式生產或送印 |
| 正式（核准並設定後） | 使用正式憑證及網址，驗證付款結果後交接生產 |

**付款方式範圍**：初版綠界只開信用卡（`ChoosePayment=Credit`），不開 ATM、超商代碼等非即時付款，因此付款狀態不需要「已取號、待繳費」。人工收款在綠界上線後可保留為備用，由設定開關決定。

### 人工收款規則

- 需要專屬權限（例：`orders.confirm_manual_payment`），以 `@require_permission` 保護；確認動作記錄操作人、時間、實收金額、轉帳末五碼及備註。
- 實收金額須等於訂單應付金額才能確認；不符時只能標記待處理並聯絡會員，不能部分確認。
- 確認收款寫入一筆付款嘗試紀錄（`provider='manual'`），付款成功後的處理與綠界通知共用同一段程式，避免兩條路徑行為不一致。
- 匯款期限逾期未確認的訂單轉為逾期取消；已確認的收款不可在後台直接改回未付款，只能走例外處理並保留紀錄。
- 這個模式不經綠界，發票須由管理者在綠界電子發票後台手動開立後回填號碼（§8）。

### 綠界串接要點

正式串接以後端 ReturnURL 通知為付款依據，驗證 CheckMacValue、商店代號、交易編號、金額與付款結果，成功處理後回應 `1|OK`；前端返回頁只顯示查詢結果。詳情在實作綠界 adapter 時按最新版文件核對。

綠界後台的模擬付款通知若含 SimulatePaid=1，只用來確認通知可接收，不得將訂單標記為已付款或啟動生產；這與使用測試卡走完整測試交易不同。

既有 `POST /webhooks/mock-payment` 已於 2026-10-03 限制為僅 `IS_DEV_MODE` 開放（其他環境回 404），且只處理待付款訂單。v2 不再使用它，綠界 adapter 完成後可移除。

## 4. 資料庫策略

沿用既有會員、命盤、商品與訂單基礎；新增結構一律以 migration 管理，採只增不改的方式擴充，維持 Claire、Happy_Wu 現行行為。

### 程式與 migration 放置位置

| 位置 | 內容 | 理由 |
| --- | --- | --- |
| `packages/commerce`（commerce 鏈） | `order_items`、`payment_attempts`、`payment_notifications`、訂單發票資料 | 各站台都會用到的通用電商能力 |
| Polaris 站台鏈 | 生產交接、成品權限、實體出貨、人工收款設定 | 依附紫微系統與本站商品 |
| 紫微系統 | `account`、`graph` 結構 | 紫微端掌管命盤寫入 |

共用的新功能由設定開關啟用；未開啟的站台維持既有 `orders.items` JSONB 寫法。`orders.items` 繼續寫入作為快照，但 v2 的權威來源是 `order_items`。

### 新增表：order_items

`shop.orders.items` 只是 JSONB 快照，沒有數量及穩定識別，無法掛生產、交付與加購關聯，因此新增訂單項目表。

| 欄位方向 | 說明 |
| --- | --- |
| 項目識別 | 內部 id 及對外穩定編號 |
| 所屬訂單 | 關聯 `shop.orders` |
| 商品與版本 | 商品、`digital`／`physical`、購買類型 `purchase`／`addon` |
| 價格快照 | 單價、幣別、數量（初版固定 1） |
| 加購關聯 | 加購實體書時指向原數位版項目 |
| 命盤關聯 | 命盤識別及當次已確認資料版本 |
| 報告主角 | 主角姓名或稱呼快照（不另建會員帳號） |

### 新增表：payment_attempts 與 payment_notifications

每次送往金流的付款都建一筆付款嘗試，對外用嘗試編號，不直接用 `order_no`：

- 綠界 `MerchantTradeNo` 上限 20 字元且只能英數字，同一編號付款失敗後不能重用。現行 `ORD-YYYYMMDD-XXXXXXXX` 有 21 字元、含連字號，不符格式。
- 嘗試編號建議格式：`P` + `YYMMDDHHmm` + 8 碼大寫英數隨機，共 19 字元。綠界測試環境是共用商店，必須有隨機段避免撞號。
- 欄位方向：嘗試編號（UNIQUE）、所屬訂單、`provider`（`ecpay`／`manual`）、環境（測試／正式）、金額、幣別、狀態（建立、已導向、成功、失敗、逾期）、金流端交易編號（UNIQUE）、付款時間、人工確認的操作人與末五碼。
- `payment_notifications` 保存每一則收到的通知原文、驗證結果與處理結果；以金流端交易編號去重，重送不重複處理。
- 同一訂單同時只能有一筆成功的付款嘗試；確認付款成功、更新訂單、建立生產需求放在同一個 transaction。

### 其他資料能力

| 資料能力 | 實作方向 |
| --- | --- |
| 會員身分 | 沿用 account.app_users 與 blog.member_profiles；Email 驗證後才建立或歸戶（§5） |
| 命盤保存 | 透過紫微 save-and-register 保存（已確認不會啟動報告生產）；紫微無出生資料版本，所以 `order_items.customization` 保存送出時的原始輸入 |
| 商品版本 | 在現有商品基礎表達數位／實體及加購價格 |
| 交易政策同意 | 訂單記錄同意時間及交易政策版本（§10） |
| 生產交接 | OWS `report_fulfillments`（`order_item_id` UNIQUE）記錄交接與同步狀態；紫微 `report_requests` 為工作單本體 |
| 成品權限 | 成品 PDF 存為紫微 `chart_artifacts`（`book_pdf`／`book_print_pdf`），檔案在 GCS；OWS 核對擁有權後向紫微取簽名網址 |
| 實體履約 | 收件資料快照、印製與物流狀態；加購連回原報告版本 |

完整表結構清單見紫微介接契約 §3、§4。graph.graph_reports 已確認是分析表，不是成品表。

## 5. Email 驗證與命盤保存順序

紫微的 save-and-register 會在 `account.app_users` 建立免密碼會員並歸戶命盤。若在 Email 驗證前呼叫，等於替未驗證的 Email 開帳號，他人也能把命盤掛到別人的帳戶下。因此：

1. 填寫與確認頁只在瀏覽器保存草稿（沿用現有 pending chart 的 sessionStorage 做法），不寫資料庫、不呼叫紫微。
2. 結帳前登入或註冊。新會員輸入 Email，收驗證碼完成驗證後設定密碼，並明確告知會建立購買帳戶；既有會員以 Email＋密碼登入。忘記密碼以 Email 驗證碼重設。
3. 登入後，後端以**登入會員本人的 Email**（不信任前端傳入值）呼叫 save-and-register，取得命盤識別。
4. 建立訂單及訂單項目，關聯命盤與已確認資料版本，狀態為待付款。

步驟 3、4 經兩個服務完成，不在同一個 transaction；以固定的提交識別支援重試，避免保存成功但建單失敗後重複建檔。

## 6. 跨系統資料契約

### 寫入權責矩陣與紫微端現況

第 1 步已核對紫微系統，寫入權責矩陣、雙方資料表變更清單、紫微端新增 API 與工作單設計見 [紫微介接契約](membership-v2-ziwei-contract.md)。重點：

- save-and-register 不會啟動報告生產。
- 紫微現行報告產線為人工操作（編輯跑 workflow → 人工審稿 → InDesign 排版），沒有工作佇列、成品 PDF 表與完成通知；v2 改為付款後在紫微端建立人工工作單（`account.report_requests`），編輯完成後上傳最終 PDF。
- OWS 對紫微 id 一律軟參照（不建 FK），跨系統寫入只經紫微 `/public/*` 服務 API。

### 官網交出的製作需求

至少包含：需求識別、訂單項目識別、會員識別、命盤識別、已確認資料版本、商品／報告類型、購買版本、付款確認時間及測試／正式環境。

### 紫微回填

至少包含：需求識別、處理狀態、更新時間、可對會員顯示的進度、需補資料或失敗代碼，以及完成時的報告識別、版本與檔案資訊。內部錯誤詳情只顯示給管理者。

紫微端可重試領取工作，但一筆購買需求只產生一次有效生產任務。成品完成後，官網核對所屬會員及交付資格再提供下載。

## 7. 狀態與例外

- 訂單付款：待付款、已付款、逾期取消、例外處理（重複扣款、金額錯誤等，見 §10）。
- 付款嘗試：建立、已導向、成功、失敗、逾期。付款失敗可建立新嘗試重試。
- 報告製作：未開放生產、待製作、製作中、待補資料、失敗、完成（紫微工作單狀態 `queued`／`in_progress`／`needs_info`／`failed`／`completed`）。另有交接狀態：待送出、已送出、送出失敗（可重送）。
- 數位交付：尚未可領取、可領取；成品完成不等於公開存取。
- 實體書：待送印、印製中、已出貨、已完成，與數位交付分開。
- 發票：未開立、已開立、作廢（僅例外處理時）。

生產失敗不重收款；通知重送不重建工作。付款後資料更正建立可追蹤的更正版本；已送印後不直接覆蓋原資料。關鍵操作保留時間及操作人紀錄。

## 8. 電子發票

台灣網路銷售須開立電子發票，綠界電子發票是與金流分開申請的服務。結帳時收集發票選項，付款確認後開立。

**目前狀態（2026-10-03）：尚無營業登記與統一編號，無法開立統一發票。** 因此：

- 發票功能以站台設定開關控制，預設關閉；關閉時結帳不顯示發票欄位，訂單發票狀態記為「不適用」。
- 資料結構與欄位驗證照本節設計先做好，取得稅籍並申請綠界電子發票後只需開啟設定。
- 依財政部網路銷售規定，個人網路銷售當月銷售額達營業稅起徵點（銷售貨物新台幣 8 萬元、勞務 4 萬元）時，應即辦理稅籍登記，並在網站揭露統一編號與營業人名稱。客製報告屬貨物或勞務、登記後是否為免用統一發票的小規模營業人，會影響是否須開發票，請向國稅局確認。
- 因此發票功能可能長期不開，或改為開立收據；網站頁尾須預留稅籍揭露位置。
- 綠界金流可用個人身分申請，但個人帳戶有收款額度限制；營業登記與否也會影響金流申請類別，申請時一併確認。

### 結帳欄位

| 開立方式 | 必填欄位 | 格式檢查 |
| --- | --- | --- |
| 會員載具（預設） | 發票通知 Email（預設帶入會員 Email） | Email |
| 手機條碼載具 | 手機條碼 | `/` 開頭，共 8 碼，後 7 碼為數字、大寫英文或 `.` `-` `+` |
| 自然人憑證載具 | 憑證條碼 | 2 碼大寫英文 + 14 碼數字 |
| 公司（三聯式） | 統一編號、公司抬頭 | 統編 8 碼數字並通過檢查碼 |
| 捐贈 | 愛心碼 | 3–7 碼數字 |

後端重新驗證所有欄位，不只依賴前端；手機條碼可於開立前呼叫綠界驗證介面確認存在。統編發票不可同時使用載具，列印與寄送方式依綠界發票 API 規格確認。

### 保存與開立

- 訂單保存發票選項快照；開立結果記錄發票號碼、開立日期、隨機碼、狀態及開立方式（API／人工）。
- 正式模式：付款成功後由後端呼叫綠界發票 API 開立，失敗則留在未開立並通知管理者補開，不阻擋報告生產。
- 人工收款與發票 API 尚未接通時：管理者在綠界發票後台手動開立後回填號碼。
- 佔位模式只收集與保存，不開立。

## 9. 通知信

所有信件由後端在狀態轉換的 transaction 提交後寄出，並寫入通知紀錄（訂單或項目、事件、收件者、寄送結果）；同一事件以唯一鍵去重，通知重送或重試不重複寄信。

| 事件 | 收件者 | 內容重點 |
| --- | --- | --- |
| Email 驗證碼 | 購買者 | 驗證碼、有效時間；不含訂單資料 |
| 訂單成立（待付款） | 購買者 | 訂單編號、品項、金額、付款方式；佔位模式寫明「付款功能尚未開放」；人工收款附匯款資訊與期限 |
| 收款確認 | 購買者 | 付款完成、預計交期、發票資訊（已開立時） |
| 待補資料 | 購買者 | 需要補充的項目及會員中心入口；不在信中重述出生資料 |
| 報告完成 | 購買者 | 可至「我的報告」下載；只附會員中心連結，不附檔案、不附免登入下載網址 |
| 實體書已出貨 | 購買者 | 物流業者、單號、查詢連結 |
| 逾期取消 | 購買者 | 待付款或匯款期限已過，訂單已取消 |
| 待人工確認收款 | 管理者 | 會員已回填轉帳資訊 |
| 生產失敗／發票開立失敗 | 管理者 | 訂單編號與後台連結；錯誤詳情只在後台顯示 |

規則：

- 信中連結以 `FRONTEND_URL` 組成並帶語系前綴；上線須設定 `FRONTEND_URL` 與 `MAIL_*`。
- 信件不含出生日期、時間、地點等敏感資料，只用訂單編號與主角稱呼辨識。
- 測試模式的信件標題加上「[測試]」，並只寄給白名單收件者。
- 寄信失敗不回滾訂單狀態，記錄後可由後台重寄。

## 10. 交易政策：客製商品不退款

依《通訊交易解除權合理例外情事適用準則》第 2 條，「依消費者要求所為之客製化給付」及「非以有形媒介提供之數位內容」可排除七日解除權，但前提是**交易前已清楚告知**，數位內容並須經消費者事先同意。民法上的瑕疵擔保與未依約交付責任不能以聲明排除，所以聲明寫成「不適用鑑賞期、不受理取消或退款，但下列例外依法處理」。正式使用前建議請法律專業人士確認。

### 交易政策頁與商品頁的聲明文字（草稿）

> 本站報告依您提供的姓名與出生資料個別製作，屬依消費者要求所為之客製化商品；數位版為非以有形媒介提供之數位內容。依《通訊交易解除權合理例外情事適用準則》，本商品不適用七日解除權（鑑賞期），付款完成後恕不受理取消或退款。下單前請務必確認出生資料正確。
>
> 下列情形不在此限，本站將視情況補正、重新製作、重新寄送或退款：
>
> 1. 重複扣款或扣款金額錯誤。
> 2. 因本站因素無法於公告期限內交付，經通知後仍無法完成。
> 3. 成品內容與您確認的資料不符（非因您提供的資料錯誤）、檔案損毀無法開啟，或實體書有印刷、裝訂瑕疵或運送毀損。
>
> 付款後如發現資料填寫錯誤，請於報告開始製作前聯絡客服；已開始製作或已送印者，是否能更正及是否另收費用，由客服個別說明。

### 結帳頁同意勾選

- 位置：付款按鈕前，預設不勾選；未勾選不能送出付款。
- 文字：「我已確認出生資料正確，並了解本商品為客製化商品，不適用七日解除權，付款後不受理取消或退款（例外情形依《交易政策》處理）。」並連到交易政策頁。
- 訂單記錄同意時間與交易政策版本號，作為日後信用卡爭議款的佐證。
- 商品頁、確認頁與「訂單成立」通知信也要簡短提示此政策。

## 12. 主要驗收條件

- 佔位模式所有路徑都不能令訂單變成已付款或啟動生產。
- 正式環境呼叫 mock-payment 回 404。
- 未完成 Email 驗證不會呼叫 save-and-register，也不會建立帳號或命盤。
- save-and-register 回傳的命盤性別、生日、時間與 `order_items.customization` 不一致時拒絕建單。
- 交接 API 失敗時訂單保持已付款、交接為待送出，重送不產生第二張工作單。
- 會員只能查看、下載自己的訂單及成品。
- 同一筆送出或付款通知重送，不重複建單、生產或寄信。
- 付款嘗試編號符合綠界格式（≤20 字元、英數字），失敗重試產生新編號。
- 人工收款只有具權限者能確認，金額不符無法確認，確認紀錄含操作人。
- 未勾選交易政策同意無法付款；訂單保存同意時間與政策版本。
- 發票欄位不合格式時後端拒絕；付款後發票開立失敗不阻擋生產，且通知管理者。
- 填寫資料可保存並正確對應訂單主角；名稱或資料相似不合併不同購買者的內容。
- 測試付款不能觸發正式分析、成品交付或實體送印。
- 實體書加購正確關聯原數位報告；兩種交付狀態可分別查看。
- 付款成功後紫微暫時不可用，需求仍可恢復處理。

## 13. 延後項目

以下為已評估但暫不實作的改進，待初版穩定後再處理：

- 權利（entitlement）層：付款成功時發出數位／實體權利，交付與加購只看權利。
- 生產需求以 outbox 方式落庫，紫微以 `SELECT … FOR UPDATE SKIP LOCKED` 加租約領取工作。
- 付款前預覽改在瀏覽器以 `@ows/ziwei-engine` 計算，不寫資料庫。
- 報告綁定引擎版本。（成品存放已改為紫微 GCS＋簽名網址，見紫微介接契約 §4.2。）
- 出生資料同時保存原始輸入與正規化值（曆法、閏月、子時跨日、真太陽時、歷史夏令時間）。
- 送禮／轉贈、ATM 與超商付款。
