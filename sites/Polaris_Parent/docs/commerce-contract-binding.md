# 外部成交對應官網契約與資格發放

更新：2026-10-14。已實作第一條受控路徑：已查證的外部成交，對應同會員的一份官網數位報告契約。尚未部署、未套用正式 migration，也未操作任何真實平台或正式訂單。

## 這一批可驗收的流程

在後台「外部訂單查證」完成以下操作：

1. 既有渠道人工匯入許可及審查期限有效，外部訂單已完成付款與購買者歸屬查證。
2. 另行建立「平台商品與官網履約對應」：填平台商品編號、官網數位報告範本品項編號（R 開頭）、官網履約政策依據、審查備註與期限。明確核准後才可用於發放。此審查不同於單純允許內部匯入證據。
3. 對已查證的外部訂單輸入官網待付款訂單編號，產生資格發放預覽。會員、品項、金額、份數、權利與既有報告資料必須通過比對。
4. 管理者核對客製對象與平台成交內容一致，勾選確認並留下備註，才可套用。預覽憑證限原操作人與該外部訂單使用，有效 30 分鐘；訂單客製資料、政策或商品對應修訂後須重新預覽。
5. 成功後，同一張官網訂單改為 `payment_method=external_verified`、`status=paid`，來源改為平台／商店／外部訂單號。發放一份報告資格，沿用既有報告工作並設為待交接。會員可在原訂單頁看到平台成交確認及無須再付官網款項的說明。

此處 paid 表示已認列查證過的外部成交；**沒有新增 `PaymentAttempt`，也沒有收取第二筆款項**。`paid_at` 是官網認列時間，不是未取得的歷史平台入帳時間。事件使用 `external_sale_confirmed`，與官網 `payment_confirmed` 分開。

目前是營運人員受控對應流程，並非平台買家自助啟用入口。目標官網訂單必須已透過既有流程完成會員、交易政策同意、出生資料及排盤建立；本功能不根據平台收據猜測或產生出生資料。人工轉帳模式的待付款單原本會顯示匯款說明，實際試行時須先與會員確認不重複匯款；任何已回報轉帳、曾有付款嘗試或已付款的訂單均阻擋對應。

## 支援範圍與拒絕條件

本批僅支援 TWD、單品項、單份 `natal-report-digital` 數位報告。平台品項單價、總額與官網成交快照必須完全相同；沒有價差或強制通過功能。

- 同一外部訂單只可對應一張官網訂單；同一官網訂單也只可對應一筆外部證據。
- 官網訂單須具有版本 1 成交契約、原官網來源、政策同意紀錄、未逾期、未付款且從未產生任何付款嘗試。
- 會員必須啟用且與外部購買者查證結果一致。
- 必須有該會員尚未交接的報告工作、命盤及人物識別；不得已有報告檔、資格、實體書、出貨或解讀工作。
- 不支援實體書組合、多份報告、專人解讀、運費、稅額、折扣、多幣別或不同售價。
- 尚未開放外部成交啟用碼、站外客製引導或平台買家自助領用。
- 此來源訂單的官網加購入口及 API 會阻擋，待完成跨渠道加購政策與模型後再開放。

平台商品對應保存範本的成交金額與權利快照，不讀取今日商品價格來決定舊成交應得資格，也不複製範本會員的出生或客製資料。建立對應表示營運人員已記錄該商品的官網履約許可，程式不會自行判定平台條款。沒有預先核准 Etsy、Creema 或 idus。

## 作廢與既有權利

已對應的外部證據仍可作廢。作廢與履約共用官網訂單列鎖；後續報告交付會重新讀取證據狀態，不得使用快取的舊 verified 狀態通過。

作廢後，會員頁顯示「後續製作已暫停」，訂單保留原成交、資格及任務歷史，新增 `external_evidence_voided` 事件。已交付報告不會刪除或追回；資格與任務的歷史狀態不冒充未曾發生。此動作不是退款、沒有對平台發送退款請求，也不復活已作廢證據。

渠道或商品對應到期／停用只阻止新的轉換；已認列契約依成交時快照保留權利。停止個別訂單的後續履約應明確作廢該筆證據。關閉功能開關也不會繞過既有外部訂單的證據檢查。

## 底層改動

新增 migration `0013_commerce_contract_binding`，接續 0012：

| 資料表 | 責任 |
| --- | --- |
| `commerce_product_mappings` | 渠道商店＋平台 SKU 唯一對應；保存版本、成交規格快照、履約政策依據、審查者及有效期限 |
| `commerce_receipt_bindings` | 外部證據與官網訂單各自唯一；保存操作人、審查內容指紋與完整核准快照 |

沿用 `commerce_intake_events` 保存每次商品對應修訂及轉換紀錄；沿用 `commerce_events` 保存外部成交認列、資格發放與證據作廢。未修改共用資料表結構。

官網人工核款與外部認列共用「已確認契約 → 資格與既有工作」函式。付款證據的建立仍由各自流程負責，沒有偽造人工付款紀錄。

鎖定順序為渠道 → 外部證據 → 官網訂單；人工核款與履約也取得同一張官網訂單鎖。轉換、來源更新、資格、任務及兩邊稽核紀錄同一交易提交。中途失敗會全部回滾。相同有效審查憑證重送會回原訂單，不再次發放資格；官網核款與外部認列同時發生時僅一條路徑成功。

## 啟用與 API

1. 於核准測試環境執行 migration 至 0013。新程式的外部訂單查閱亦會讀取關聯表，故應先完成 migration。
2. 開啟 `COMMERCE_FOUNDATION_ENABLED`，讓新官網訂單建立契約。
3. 開啟 `COMMERCE_INTAKE_ENABLED` 以操作外部證據，並另開啟 `COMMERCE_BINDING_ENABLED` 以維護商品對應及發放資格；新開關預設 false。
4. `report_orders.channels` 可管理商品對應；新增 `report_orders.contracts` 可預覽及核准契約轉換。使用整個後台入口另需 `report_orders.intake`。單有人工核款或查證權限不能發放外部資格。
5. 無須開啟啟用碼開關。此路徑直接使用已有會員與報告資料，不發外部啟用碼。

API 前綴 `/api/v1/admin`：

| 方法／路徑 | 用途 |
| --- | --- |
| GET / POST `commerce-product-mappings` | 查看／建立或修訂商品對應；修訂須附目前 revision，並以 channel_revision 防止覆蓋新渠道設定 |
| POST `commerce-receipts/{id}/contract-preview` | 傳 order_no，回傳比對計畫、政策／商品版本、金額權利與 review_token |
| POST `commerce-receipts/{id}/contract` | 傳 review_token、confirmed=true、note，原子套用契約轉換 |

資料表已有對應或轉換紀錄時，downgrade 會拒絕刪表。回退功能請關閉新轉換開關並保留既有證據檢查與稽核資料。

## 驗證

測試不讀 `.env`，不連真實排盤、寄信、平台或正式資料庫。

- 原有與本批整合回歸 134 項通過；另補充「待確認轉帳不得轉換」及「兩張外部訂單不得支付同一契約」2 項，共覆蓋 136 項。
- 本批測試檔含 14 項新情境及 9 項基礎相容性情境：一次發放、證據作廢、舊快取、政策／客製變更、憑證期限與操作人、權限、金額／會員不符、既有核款、交易回滾、不支援的商品、查閱與加購限制。
- 一次性 PostgreSQL 18 通過 0010～0013 migration 升級／空表回退／再升級、ORM 欄位對照、並行核准、外部認列與人工核款競爭、作廢後快取刷新及有資料時拒絕刪表；此前核款、啟用碼、回填、匯入與查證並行檢查也通過。
- 前端 TypeScript 檢查通過。尚未執行瀏覽器視覺驗收及正式營運驗收。

下一批應補上安全的測試環境端到端驗收；再依實際商品與平台許可，逐項擴充實體書／組合契約、外部會員領用及退款／撤銷。真正對外派工與通知的 outbox／重試仍是獨立待辦，這一批只建立持久化待交接工作。
