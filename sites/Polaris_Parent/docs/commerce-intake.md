# 外部訂單查證帳本

更新：2026-10-14。此批完成渠道審查設定、外部成交證據的人工匯入與查證，以及後台操作頁。尚未部署，未變更正式資料庫，也沒有連接任何平台。

## 操作入口與範圍

後台「訂單 → 外部訂單查證」，路徑 `/admin/commerce-intake`。

1. 管理者建立渠道與商店識別，填寫政策審查依據、備註和下次審查期限，明確選擇是否允許內部人工匯入。
2. 匯入平台訂單編號、購買會員編號、TWD 成交總額與成交品項。匯入結果為「待查證」。平台商品編號只是證據，不對應內部商品或資格。
3. 到可信的平台後台／原始紀錄核對付款、金額、商品與購買者歸屬，填寫證據參照及備註，再勾選付款與歸屬確認。
4. 審查結果可為「證據已查證」或「已否決」；待查證／已查證都可作廢。否決或作廢不能重新啟用，也不開放覆寫原始成交快照。需更正時保留原紀錄，後續由例外處理流程處理，不使用虛構新訂單號繞過去重。
5. 每筆外部訂單可查看匯入、查證與作廢的操作者、時間、渠道版本及依據。

**證據已查證不代表官網已收款，也不代表已發放資格。** 匯入與查證本身不建立官網訂單、付款、資格或任務。後續新增的 [契約對應與資格發放](commerce-contract-binding.md) 需要獨立商品履約審查、權限與核准步驟，目前僅支援單份數位報告；不建立官網付款紀錄、不寄信、不自動派工。

渠道設定屬營運人員的內部審查紀錄，程式不會替人員判斷平台條款。未預先建立或核准 Etsy、Creema、idus 的能力。站外啟用、站外客製與 webhook 欄位目前固定回傳 `false`，沒有可開啟的實作。內部人工匯入許可不能拿來推論平台允許站外啟用。

## 底層結構

新增 migration `0012_commerce_intake`，接續 `0011_commerce_activations`，建立本站擁有的三張 `shop` 資料表；不修改共用資料表。

| 資料表 | 責任 |
| --- | --- |
| `commerce_channels` | 渠道＋商店唯一識別、目前審查版本、人工匯入開關、審查依據與期限 |
| `commerce_external_receipts` | 外部成交快照、會員、金額、品項、內容指紋、查證狀態及渠道版本 |
| `commerce_intake_events` | 渠道設定每次修訂的完整快照，以及訂單匯入／查證／作廢稽核紀錄 |

訂單以渠道商店＋平台訂單編號唯一。內容相同的重送回傳原紀錄；會員、金額或品項不同則回傳衝突，禁止覆寫。同渠道的匯入／查證與設定更新先取得渠道列鎖，查證再取得訂單列鎖。資料及稽核事件同交易提交，寫入失敗一起回滾。

渠道修訂需帶入目前版本；匯入與查證也檢查版本，查證另檢查成交內容指紋。版本不符必須重新載入、重新核對。政策過期或停用會阻擋匯入與確認證據，但仍允許否決／作廢。更新渠道版本時，畫面清空未提交的審查勾選。

付款證據採人工查證參照，不下載連結、不接收未驗簽 webhook，也不把任意請求內容當作平台證明。不要在備註放出生資料、卡號、完整銀行帳號或存取憑證；原始文件應保存在受權限控制的既有證據儲存位置。

## 啟用與權限

- 原始帳本結構為 0012；合併契約對應功能後，新程式須先於核准測試環境執行 migration 至 0013，再設定 `COMMERCE_INTAKE_ENABLED=true`。預設為 false；關閉後只可查閱，所有新增／更新停止。
- `report_orders.intake`：查看渠道、匯入、查證及查看訂單稽核紀錄。
- `report_orders.channels`：建立／修訂渠道設定。操作完整後台頁面需同時擁有 `report_orders.intake`；僅具訂單審查權限者不能改設定。
- 所有 API 需登入且會員啟用，寫入另有速率限制。API 不要求兩名不同人審查；若需雙人覆核，須另設角色與流程。
- migration downgrade 只允許三張表全部為空時執行；已有審查資料時必須保留稽核歷史。

## 管理 API

下列路徑前綴為 `/api/v1/admin`。

| 方法／路徑 | 用途 |
| --- | --- |
| GET / POST `commerce-channels` | 查看／建立渠道（channels 權限） |
| PUT `commerce-channels/{id}` | 帶 revision 修訂渠道（channels 權限） |
| GET `commerce-intake-channels` | 查證人員唯讀查看渠道與功能開關 |
| GET / POST `commerce-receipts` | 每頁 50 筆查閱／匯入外部訂單；下一頁使用回傳 next_before 作 before 參數 |
| POST `commerce-receipts/{id}/review` | 帶 fingerprint、channel_revision、decision、note、evidence_reference 查證；verified 另需兩項確認為 true |
| GET `commerce-receipts/{id}/events` | 查看訂單稽核紀錄 |

匯入格式範例（僅為測試資料）：

```json
{
  "channel_id": 1,
  "channel_revision": 1,
  "external_order_id": "TEST-001",
  "member_id": 1,
  "currency": "TWD",
  "amount": 200,
  "lines": [{"external_sku": "test-book", "quantity": 2, "unit_amount": 100}]
}
```

目前只接受正整數單價、數量及 TWD 金額，品項加總必須等於成交總額。尚未建模折扣、稅額、運費、多幣別或部分退款；遇到這些訂單應先定義對應的成交模型，不能挪動金額假裝核對成功。

## 驗證與後續

- 新增 9 項隔離測試：匯入與查證重送、內容衝突、停用／到期、過期版本、付款與歸屬確認、作廢與終態、輸入及權限、交易回滾、唯讀及稽核存取。
- 與交易骨架、啟用碼、歷史回填及既有報告／實體／設計／交付合跑：113 項通過。
- 一次性 PostgreSQL 18：0010～0012 升級／空表回退／再升級、ORM 欄位對照、並行匯入與查證只產生一筆紀錄、已有資料禁止回退；既有並行核款、發碼、兌換與回填檢查也通過。
- 前端 TypeScript 檢查通過。尚未進行瀏覽器視覺驗收與正式環境驗收。

後續已完成 [單份數位報告的商品對應與受控資格發放](commerce-contract-binding.md)，verified 仍不會自動觸發發放。實體組合、會員自助領用、平台退款仍待擴充；不能直接將 verified 視為官網 PaymentAttempt 成功。
